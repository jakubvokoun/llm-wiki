# Prometheus on Kubernetes: native service discovery and appliance-port gotchas

Moving a [Prometheus](../entities/prometheus.md) stack from a single host (or a Docker Compose appliance) onto [Kubernetes](../entities/kubernetes.md) is not a lift-and-shift. The discovery model, the per-node coverage model, and the identity-label model all change, and a naive 1:1 port of each Compose service to a Deployment produces a stack that scrapes the wrong things, double-counts, or silently covers only one node. The reusable lesson: stop porting services and adopt **API-driven discovery** (`kubernetes_sd_config`), let the platform provide what it already provides (the kubelet's cAdvisor, the API server), and reserve DaemonSets for the genuinely node-local pieces. This page is the pattern plus the non-obvious gotchas that cost the most debugging time.

It assumes Prometheus running **in-cluster** (its own ServiceAccount, scraping over the pod network), with [Grafana](../entities/grafana.md) for dashboards. See [Prometheus instrumentation](../concepts/prometheus-instrumentation.md), [observability](../concepts/observability.md), and [Kubernetes observability](../concepts/kubernetes-observability.md).

## Why a 1:1 Compose/host port fails

Each of these is structural, not a config bug — the Compose shape has no correct Kubernetes equivalent as a plain Deployment:

| Concern                    | Naive port                                                                                                                                | Kubernetes-native fix                                                                                       |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Per-node coverage          | `node_exporter` as a single-replica Deployment — scrapes exactly one node                                                                 | **DaemonSet** (one pod per node)                                                                            |
| Container metrics          | a `cadvisor` Deployment mounting `/var/lib/docker` — Docker-only, broken on containerd                                                    | **drop it**; scrape the kubelet's built-in cAdvisor at `/metrics/cadvisor` via the `node` role              |
| Textfile collector sharing | Compose shared one named volume across `node_exporter` + several writer exporters; per-Deployment `emptyDir`s no longer share a directory | co-locate the writer exporters as **sidecars in the `node_exporter` DaemonSet pod**, sharing one `emptyDir` |
| Target discovery           | Prometheus reads a host file (`file_sd`) generated by some external discovery process                                                     | **`kubernetes_sd_config`** — no host files, no external generator                                           |
| Cluster-object metrics     | absent on a host appliance                                                                                                                | add **kube-state-metrics** (Deployments, Pods, PVCs, Jobs, ...)                                             |

The throughline: anything that was "one process per host" becomes a DaemonSet, anything the platform already exposes (cAdvisor, the API server) is scraped in place rather than re-deployed, and discovery moves from files to the API.

## `kubernetes_sd_config`: roles and relabeling

Discovery is driven by **roles**, each yielding targets with `__meta_kubernetes_*` labels you keep/rewrite via `relabel_configs`. The roles you actually need:

| Role                  | Discovers                                                                              | Key meta-labels                                                                                                                         |
| --------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `node`                | one target per node = kubelet address (`:10250`, HTTPS)                                | `__meta_kubernetes_node_name`, `__meta_kubernetes_node_label_*`, `__meta_kubernetes_node_address_InternalIP`                            |
| `pod`                 | one target per declared container port                                                 | `__meta_kubernetes_namespace`, `__meta_kubernetes_pod_name`, `__meta_kubernetes_pod_annotation_*`, `__meta_kubernetes_pod_node_name`    |
| `endpoints`           | one target per endpoint addr+port; joins backing-pod + service labels                  | `__meta_kubernetes_service_name`, `__meta_kubernetes_service_annotation_*`, `__meta_kubernetes_endpoints_name`, plus the `pod_*` labels |
| `endpointslice`       | like `endpoints` via the EndpointSlice API                                             | preferred at scale; `endpoints` is fine until then                                                                                      |
| `service` / `ingress` | one target per service port / ingress path (used with a blackbox exporter for probing) | `__meta_kubernetes_service_*` / `__meta_kubernetes_ingress_*`                                                                           |

A typical scrape config has a handful of jobs: `kubernetes-apiservers` (`endpoints`, keep only the `default/kubernetes/https` endpoint), `kubernetes-nodes` and `kubernetes-cadvisor` (both `node`, the latter with `metrics_path: /metrics/cadvisor`), `kubernetes-service-endpoints` and `kubernetes-pods` (annotation-driven app discovery). The de-facto annotation convention the endpoints/pods jobs key on: `prometheus.io/scrape: "true"`, `prometheus.io/path`, `prometheus.io/port`, `prometheus.io/scheme`. An exporter Service that carries those annotations self-registers with **no new job**.

**In-cluster auth and RBAC.** Running in-cluster, Prometheus authenticates to the kubelet and API server with its pod ServiceAccount token + CA under `/var/run/secrets/kubernetes.io/serviceaccount/`; no `api_server:` field is needed. Discovery and node scraping are **cluster-scoped**, so the SA needs a **ClusterRole** (not a Role):

```yaml
rules:
  - apiGroups: [""]
    resources:
      ["nodes", "nodes/metrics", "nodes/proxy", "services", "endpoints", "pods"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["discovery.k8s.io"]
    resources: ["endpointslices"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["networking.k8s.io"]
    resources: ["ingresses"]
    verbs: ["get", "list", "watch"]
  - nonResourceURLs: ["/metrics", "/metrics/cadvisor"]
    verbs: ["get"]
```

This cluster-wide read of nodes/endpoints/pods is the one genuinely new permission surface the migration introduces — see [RBAC](../concepts/rbac.md) and [Kubernetes security](../concepts/kubernetes-security.md). Pair it with a [NetworkPolicy](../concepts/network-policy.md) once the scrape graph is stable.

## Scraping a DaemonSet correctly (the headless-Service trick)

This is the gotcha that silently breaks per-node monitoring. A DaemonSet pod must **not** be fronted by a normal ClusterIP Service: a ClusterIP load-balances, so discovering it as a single service target collapses per-node scraping to **one random node per scrape**. The fix:

- Front the DaemonSet with a **headless Service** (`clusterIP: None`) selecting its pods, with one **named port per directly-scraped exporter**.
- Discover it with the `endpoints` (or `endpointslice`) role: each node's pod becomes one endpoint address, each named port becomes its own target → genuine per-node, per-exporter coverage.

Node-local sidecars then split into two classes, and only one is scraped directly:

| Sidecar class                             | Port?          | How Prometheus gets the metrics                                                                                                                                                  |
| ----------------------------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Textfile-writer** (write `.prom` files) | none           | writes into the shared `emptyDir`; `node_exporter`'s `--collector.textfile.directory` serves them on its own port. Scraped **through** `node_exporter`, not as separate targets. |
| **Direct-scrape** (expose `/metrics`)     | own named port | becomes its own target via the headless Service + `endpoints` role                                                                                                               |

App exporters that are **not** node-local (a cache, a database, a log shipper) stay as ordinary single-replica Deployments behind a normal annotated ClusterIP Service — one-port-per-Service `endpoints` discovery, no headless trick required.

## `honor_labels: true` for exporters that expose their own identity

The annotation-driven `endpoints`/`pods` jobs relabel a target's `namespace`/`pod`/etc. from the **scrape target's own** service location. But some exporters — kube-state-metrics above all — expose series whose `namespace`/`pod` labels describe **other** objects across the cluster. Without `honor_labels: true` on those jobs, Prometheus overwrites the exporter's labels with the scrape target's location, collapsing every `kube_*` series to the monitoring namespace and breaking all multi-namespace queries. Set `honor_labels: true` on jobs that scrape label-bearing meta-exporters so the exposed identity labels win.

## Per-target auth needs a dedicated SD job

A common false conclusion is "this target needs credentials, so it can't be auto-discovered — pin it as a static target." Half-true. The _generic_ annotation job can't carry per-target basic-auth/TLS, but a **dedicated SD job can**: auth, scheme, and TLS are configured at the **job level**, while service discovery only _selects_ which targets the job scrapes. So an authenticated endpoint over HTTPS still gets full SD benefits (per-pod targets, survives pod-IP churn, scales to multiple replicas) — give it its own job with job-level `basic_auth`/`tls_config`, and have its Service self-register via a **distinct** annotation marker (e.g. a custom `scrape-secure` annotation) so the generic job ignores it and you don't double-scrape with a 401. Prefer this over static targets, which round-robin to a single pod behind a service FQDN.

## Roll-your-own vs the operator

Two viable shapes:

- **Roll-your-own** — a plain Prometheus Deployment/StatefulSet + a hand-written scrape ConfigMap + RBAC + PVC, with node-local exporters folded into one DaemonSet. Fewer moving parts, full control of the config, no CRDs; you maintain the scrape config by hand.
- **kube-prometheus-stack (Prometheus Operator)** — ServiceMonitor/PodMonitor CRDs, bundled exporters and dashboards, ~10 images. Less config to write, but it sidelines custom exporter images and adds an operator + CRD surface to learn and secure.

For a single cluster or a POC, roll-your-own is usually the faster path to a correct, legible stack. Reach for the operator when monitoring must scale across many clusters or teams and the CRD-driven, self-service `ServiceMonitor` model earns its overhead. Decide deliberately — the operator is hard to back out of once dashboards and alerts assume its CRDs.

## Dashboard rule: never let `instance` define a series

Every scrape target carries `instance = <podIP>:<port>`, and a pod reschedule mints a **new** `instance`. A [Grafana](../entities/grafana.md) panel whose series identity includes `instance` therefore draws a **duplicate line with the same legend** for one logical entity across any window spanning a restart — the old series lingers (stale, but present until retention expires) beside the new one. The rule:

- Aggregate every target-level expression by a **stable identity label** — `node`, `cluster`, `service`, `component` — and legend on that, never on `instance`.
- `max by (<id>) (...)` for gauges/instant values (picks one during the brief old/new overlap), `sum by (<id>) (rate(...))` for counters.
- Re-key node dashboards on `node` (it survives `node_exporter` pod restarts), not `instance`.
- The one deliberate exception is per-target **diagnostic** panels (scrape duration, samples-per-target, down targets) where `instance` _is_ the subject.

This compounds with the headless-Service point: per-node DaemonSet targets churn their `instance` on every node-agent restart, so node dashboards must key on `node` to stay single-lined. See [Prometheus recording rules](../concepts/prometheus-recording-rules.md) for pre-aggregating these, and [four golden signals](../concepts/four-golden-signals.md) for what to put on them.

## Deployment gotcha: `hostNetwork` single-replica needs `Recreate`

A single-replica Deployment that uses `hostNetwork` (or otherwise claims a fixed host port — common when adding an exporter sidecar that binds a host port) deadlocks under the default `RollingUpdate` strategy: the surge pod can't schedule because the old pod still holds the host port (`FailedScheduling: didn't have free ports`), and the old pod won't terminate until the new one is ready. Set `strategy.type: Recreate`. This often lies latent until the first rollout — adding a metrics sidecar is a frequent trigger because it forces a previously-never-rolled pod to redeploy.

## Recommendation

- **Discovery:** `kubernetes_sd_config` everywhere; drop host `file_sd` and any external discovery generator.
- **Node-local agents:** one `node_exporter` DaemonSet, textfile-writer exporters as sidecars sharing an `emptyDir`, fronted by a **headless** Service discovered via `endpoints`.
- **Platform metrics:** scrape the kubelet's built-in cAdvisor (no cadvisor pod); add kube-state-metrics with `honor_labels: true`.
- **Authenticated targets:** dedicated SD jobs with job-level auth, not static targets.
- **Dashboards:** key every panel on a stable identity label; reserve `instance` for diagnostics.
- **Topology:** roll-your-own for one cluster; operator only when the `ServiceMonitor` model pays for itself at scale.

The deeper generalization: on Kubernetes, monitoring is **discovered, not configured** — design the stack around the API's view of what's running, and treat anything that still needs a hand-maintained target list or a per-host process as a smell to re-architect.
