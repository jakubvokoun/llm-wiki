# OpenBao — Architecture

How [OpenBao](../entities/openbao.md) processes requests and protects data internally.

## Key Takeaways

- **Barrier:** the encryption layer that encrypts/decrypts all OpenBao data. The storage backend sits _outside_ the barrier and is treated as untrusted — raw storage access yields only ciphertext.
- **Seal/unseal:** the server starts **sealed**. Initialization generates an **encryption key** (protects all data), itself protected by a **root key**, which is protected by the **unseal key**. By default the unseal key is split via [Shamir's Secret Sharing](../concepts/openbao-seal-unseal.md) into shards; auto-unseal via cloud KMS/HSM is an alternative.
- After unsealing, OpenBao loads audit devices, auth methods, and secrets engines (all stored inside the barrier and ACL-protected).
- **Core:** manages request flow — enforces ACLs and ensures audit logging. Auth methods return a policy list; a **client token** is generated by the token store and used for future requests.
- **Policies** are named ACL rules; OpenBao is **default-deny** (allow only what a policy explicitly grants). The system backend is always mounted at `sys/`.
- On a secret read, the core registers it with the **expiration manager** and attaches a **lease ID**; leases are auto-revoked on expiry. Partial failures use write-ahead logging + a rollback manager.
